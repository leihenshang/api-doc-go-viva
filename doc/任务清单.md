### N13 JSON 请求体编辑器：行号与折叠（文档源码区已完成前半）

- **现状**：`TextArea` 只给纯文本，没有行号、没有折叠，也拿不到光标与选区。
- **v0.6.8 起**：`ui/codeeditor` 提供带行号栏（gutter）、当前行高亮、按字节范围装饰的编辑器，文本模型是应用自己的 `*text.Editor`；行号这条路不再需要自绘，但按键 / 指针 / 输入法要按它的约定接（`codeeditor.Editor.Key/Pointer/Text`）。折叠仍无现成支持。
- **2026-11-20 尝试**：先给「响应正文」的只读视图加行号（左侧窄槽 + 折叠箭头右移）。实现本身能画出来，但改动了正文的 x 原点后 `handlePointer` 的箭头列判定与选区起点一起偏了，`TestSelectionTracksPointer` 直接选不出东西；同一次尝试还暴露出 viva 的 `Driver.Chord` 依赖「聚焦的文本终端」，指针在正文上按下会把焦点收回页面。
- **结论**：只读视图的行号可以单独立项做（不动 `sel.x`，把行号画在正文右侧或状态栏），但可编辑编辑器的行号 + 折叠必须有 viva 的 `TextArea` 光标/选区接口，强行自绘会把中文输入法（见 `doc/ime-linux.md`）一起搭进去。
- **可先做的降级**：拆成 N22（只读视图行号，不动 `sel.x`）。
- **2026-11-24**：文档源码区已迁 `ui/codeeditor`（行号 / 当前行高亮 / 折行 / 选区 / 滚动条），见 `internal/view/docode.go`；正文真源仍是 `m.editor.text`，编辑器只是镜像。剩下的折叠与语法高亮继续等上游。
- **2026-11-25 真窗口的两个坑，同一个根因**：`ui/codeeditor.View` 的 wrapper 先以 `RoleTextField` 声明了一个**没有文本几何**的命中（`Multiline=false`、`Placement=nil`），而 `interaction.TextInputHit` 取的是「第一个 `RoleTextField` 命中」。于是平台文本层把这篇多行 Markdown 当单行处理：
  1. **焦点一进来，源码区底部多一行文字**：单行字段才会走「自己再画一遍光标所在行」（`internal/platform/linux/text_input_linux.go` 的 `rebuild`），`docCodeInput` 现在把交给平台的 `Bounds` 缩成编辑器右下角 1×1，那块裁剪矩形只剩 1 像素，字就画不出来（`Color` 给底色兜底）。
  2. **点正文不移动插入符**：没有 `Placement` → `Placed=false` → 平台自己接管按下，只按 x 换算插入符（点哪都跑到开头几行），并把应用算好的位置覆盖掉。
  - **做法**：源码区不再用 wrapper，自己 `ui.Control` 声明控件、自己调 `components.CodeEditor.Paint`（`docSourcePane` / `docCodeDraw`），控件角色让成 `RoleGroup`；文本服务改由页面级 `Config.TextInput` 按控件身份回答（`docTextService`）。命中里只剩组件那一份（`Multiline=true`、`Placement=*CodeEditor`），平台既不抢指针也不抢插入符，插入符交给框架的 `placeCaret`（双击选词、拖动拉选区都由它做），`docCodePointer` 只转发滚动条拖动。
  - 用例：`TestDocCodeHitIsPlaced`（守住命中必须是多行 + 带 Placement）、`TestDocCodePointerMovesCaret`（点中第 N 行，插入符不能停在末尾）、`TestDocCodeInput`（Editor + 底色）。前者在角色退回 `RoleTextField` 时会连同后两者一起失败。
- **下一步**：等 viva 暴露 `TextArea` 的光标/选区（需求见「上游待办 → 文档源码区」），再一次性做「行号 + 折叠 + 语法高亮」。

### N17 CI 流水线

- **现状**：仓库没有 `.github/`；`scripts/check.sh` 已经是完整门禁（gofmt → build → vet → test，含无头界面用例），只差没人自动跑。

- **风险**：低。唯一不确定是 CI 容器里无头用例是否需要 `VK_ICD_FILENAMES`，本机就是 lavapipe，照抄即可。

### N18 OpenAPI YAML 导入

- **现状**：`importers/openapi.go` 交给 `share/openapi.Decode`，那里只做 `json.Unmarshal`；YAML 直接报「解析 OpenAPI: invalid character」。对话框文案与占位符也写死 JSON。
- **范围**：首字符不是 `{` / `[` 时用 `gopkg.in/yaml.v3` 转成 JSON 再交给 `Decode`（键必须是字符串，遇到数字键给出可定位错误）；对话框说明与文件过滤器加 `*.yaml,*.yml`；导入摘要里注明「YAML 已转换」。
- **验收**：同一份文档的 YAML 与 JSON 两个版本导入后，条目数、方法、地址、参数逐项相同；Swagger 2.0 的 YAML 仍给「请先转换」。
- **风险**：低。转换放在 viva 的 importers 里，不动 share 这个共用模块。

### N25 请求页 tab 与 Wails 版对齐（缺 4 个）

对比 Wails 版（2026-11-26）：Wails 的请求页有 9 个 tab——请求参数 / 请求体 / 请求头部 /
认证 / 响应字段 / 变量 / 脚本 / 断言 / 文档；viva 是 5 个（`model.go` 的 `httpSegments`）：
参数 / 请求体 / 请求头 / 认证 / 文档。缺的四项：

- **响应字段**（Wails `ResponseFields.vue` + `useResponseFields.ts`）：把上次响应的 JSON 字段
  点选成变量，供后续请求 `{{变量}}` 引用。viva 只有「运行规则」弹窗里的提取规则，得手写路径。
- **变量**：请求级临时变量（只在这次请求生效，覆盖环境同名值）。viva 目前只有环境级变量。
- **脚本**：请求前/后脚本钩子。viva 完全没有，且涉及「执行用户代码」的沙箱问题，需要单独立项评估。
- **断言**：请求页上直接配断言并随发送执行。viva 的断言在「运行规则」（`dialogs.go:784`）
  里，且只有跑集合时才走，单发请求不判定成败。

另有命名与细节差异：viva 叫「参数 / 请求头」，Wails 叫「请求参数 / 请求头部」；
Wails 的「文档」tab 右上角有未保存小绿点，viva 没有。

建议顺序：**响应字段 → 变量 → 断言 → 脚本**（脚本风险最高，放最后并单独评估）。

### N26 MCP 与 Wails 版对齐（2026-11-26 已补全）

对比 Wails 版（2026-11-26）。viva 已有：启用开关、监听地址、只读模式、工具组勾选、可访问工作区、令牌、客户端连接与配置 JSON、运行状态。缺的三项：

- **来源白名单（allowOrigins）**：后端 `internal/mcp/server.go` 已支持（`AllowOrigins` 为空时拒绝一切带 Origin 的请求，防 DNS rebinding），但 `startMCP` 没传这个字段，设置面板也没有输入框。后果是浏览器类 MCP 客户端一律连不上，用户也无处可改。这是三项里最该先补的：一行传值 + 一个文本框。
- **调用审计面板**：审计文件已经在写（偏好目录下 `mcp-audit.jsonl`，见 `internal/view/mcp.go`），但界面上没有查看 / 导出 / 清空入口；Wails 有 `McpAuditPanel.vue`。
- **写操作授权确认**：Wails 在 AI 要写磁盘或发请求时弹 `McpConsentDialog.vue` 让用户确认；viva 只有只读模式与工具组勾选这类事前约束，运行中无法逐次拦截。

**已补全**（2026-11-26）：

- 来源白名单：`settings.MCPAllowOrigins` + 面板输入框（`parseMCPOrigins` 去空格/去重），启动时传给 `HTTPOptions.AllowOrigins`；

用例：`TestMCPOrigins`、`TestMCPOriginsField`、`TestMCPConsentAnswers`、`TestMCPConsentOneAtATime`。

### N23 运行器并发 / 重跑失败（先评估）

- **现状**：`runner.Run` 顺序执行，`Options` 只有 `StopOnFailure` / `Vars`；`Vars` 会被前一条的 `extract` 覆盖，形成隐式依赖链。
- **结论**：不能直接加 `--jobs N`，会破坏 `{{token}}` 链。要并发得先做「无 extract 的批」或显式 `dependsOn`，两样都会改格式或加规则。
- **先做低风险的**：界面「只重跑失败项」；`apidocctl run --retry 1`（单条重试，不动变量袋语义）。

### 变量悬停（应用层方案已解决，只剩两条边界）

2026-11-25 结论：**不改框架、也不自绘**。指针进入某个 `{{变量}}` 的矩形时，在 `Slot.Draw` 里用
`canvas.HitLabel(字段ID, 变量矩形, "", false)` 声明一条标签热区（按下按标签语义交回输入框），
再用 `canvas.HintSince` 给它补提示文字——提示仍由框架画，锚点就是那一小段矩形，所以会跟着文字走。
指针落在框里其他位置时，压一条不带 Hint 的标签热区把整框那条提示盖掉（同一个 ID 取最上层热区，
空 Hint 就是不弹）；字段自己那条 `Tooltip` 只为满足 `HasTooltip`，永远不显示。实现在
`internal/view/varhover.go`，机制由 `hovertarget_test.go` 守着，行为由 `vartip_test.go` 的无头用例守着。

剩下的两条边界都是「坐标算不准」，不是缺 API：

1. `ui.TextArea` 折行之后逐字坐标要做软换行计算，现在仍只有整条框的提示；
2. 聚焦且文字超宽的单行输入框，平台会横向滚动而 canvas 上的文本留在原位（`canvas.Texts()` 的原点不变），
   这类输入框不弹提示（而不是弹一个位置错的）。彻底解决需要框架把「文本原点 + 横向滚动偏移」交给应用。

如果上游哪天给出「只悬停、不接管按下」的热区（`gfx.HitOptions` 加一个标记），热区就能常驻声明、
不必每帧算是否命中，代码能少一截——属于优化，不再是必需。
